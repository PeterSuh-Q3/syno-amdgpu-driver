# Synology AMD+i915 Dual DRM and Runtime 통합 설계

## 목표

목표는 Mesa VA-API/Vulkan 사용자 공간, 플랫폼별 전체 DRM 모듈 묶음, AMD/i915 펌웨어를 설치형 SPK로 제공하는 것이다. 커널 ABI별 SPK를 하나씩 제공하며, 각 패키지에는 해당 커널 계열의 지원 플랫폼 전체 모듈 묶음을 넣고 설치 시 감지한 플랫폼에 맞는 묶음만 적용한다.

제품은 커널 ABI별 통합 SPK로 제공한다. DSM 7.4 kernel 5.10.55용 6개 플랫폼 SPK와 kernel 4.4.302용 10개 플랫폼 SPK를 각각 만들며, 설치 시 `synoinfo`와 실행 중인 커널을 기준으로 일치하는 묶음만 선택한다. 이 릴리즈는 DSM 7.4를 대상으로 하며 DSM 7.0–7.3 모듈은 포함하지 않는다.

## 설계 결정

1. **DRM 아카이브는 분해하거나 필터링하지 않는다.** 각 플랫폼의 `*-drm.tgz`를 원형 보존한다. AMD와 i915 모듈을 분리하는 절차는 두지 않는다.
2. **커널 ABI마다 통합 SPK 하나를 제공한다.** DSM 7.4 kernel 5.10.55의 6개 플랫폼 또는 kernel 4.4.302의 10개 플랫폼 모듈 묶음을 각각 한 SPK에 담는다. 설치기는 DSM 플랫폼과 커널을 판별해 해당 모듈 묶음만 설치한다. 기존 패키지 ID `syno-amdgpu-runtime`은 유지한다.
3. **모듈 및 펌웨어 소스는 버전과 SHA-256으로 고정한다.** 릴리즈 이름만 신뢰하지 않고, 빌드 전에 입력 아카이브의 체크섬을 검증한다.
4. **설치는 트랜잭션으로 처리한다.** 플랫폼·커널을 정확히 식별하지 못하거나 파일 백업·복구 준비가 실패하면 시스템 파일을 변경하지 않고 중단한다.
5. **실행 중인 DRM 모듈은 강제로 내리거나 교체하지 않는다.** 설치는 다음 부팅 적용을 기본으로 하며, 재부팅 없이 성공한 것처럼 보고하지 않는다.

## 기준 자산 및 대상

기준 모듈은 [tcrp-modules 26.9.12 릴리즈](https://github.com/PeterSuh-Q3/tcrp-modules/releases/tag/26.9.12)의 DSM 7.4 `*-drm.tgz`이다. 두 펌웨어는 [`firmware/common`](https://github.com/PeterSuh-Q3/tcrp-modules/tree/main/firmware/common)의 `firmwareamdgpu.tgz`와 `firmwarei915.tgz`를 사용한다. 입력은 저장소 커밋 `429c12eccafab48a0f6a8309ac3626a54a9b0eaa`에 고정한다. AMD 펌웨어 SHA-256은 `c24525d644dbcd8dc7c5777be7223ca8c5236d2487314dd3810a223f7dcc6225`, i915 펌웨어 SHA-256은 `443c13a6f5d474251b3750b8bcbceea21fb9998595287bb750b7bf4f9199ca8e`이다. 소스 갱신 시에는 커밋·릴리즈와 체크섬을 함께 의도적으로 변경한다.

26.9.12의 7.4 모듈 자산은 16개 타깃이다.

| 커널 계열 | DSM 7.4 플랫폼 |
|---|---|
| 4.4.302 | `apollolake`, `broadwell`, `broadwellnk`, `broadwellnkv2`, `broadwellntbap`, `denverton`, `geminilake`, `purley`, `r1000`, `v1000` |
| 5.10.55 | `epyc7002`, `epyc7003`, `geminilakenk`, `icelaked`, `r1000nk`, `v1000nk` |

각 통합 SPK에는 표의 해당 커널 계열 플랫폼별 모듈 아카이브를 각각 포함한다. 같은 커널 버전이라는 이유로 플랫폼 간 모듈을 혼용하지 않으며, 설치기는 호스트와 일치하는 한 묶음만 선택한다. DSM 7.4의 kernel 5.10.55 및 4.4.302 패키지를 제공한다. DSM 7.0–7.3은 별도 자산과 검증 후 추가한다.

## DRM 모듈 묶음 정책

타깃의 `*-drm.tgz`는 `amdgpu.ko` 외에도 DRM 공통 모듈과 호환 모듈을 함께 제공한다. 26.9.12 `epyc7002` 예시에서는 `amdgpu.ko`와 `drm.ko`가 `i915-compat.ko`를 의존한다. 따라서 이름에 `i915`가 포함된 파일을 단순 제거하면 AMD 모듈도 필요한 의존성을 잃을 수 있다.

패키징은 아카이브를 통째로 보존하고, 파일 목록·체크섬을 빌드 기록에 남긴다. 설치 시에도 해당 묶음을 같은 타깃의 DRM 세트로 취급한다. 이 설계는 개별 `.ko`의 선별 복사, 이름 기반 제외, 다른 플랫폼 묶음과의 혼합을 금지한다. 커널 4.4.302 자산도 동일한 완전 묶음 정책으로 처리한다.

Intel DRM 장치와 AMD GPU가 공존하는 NAS는 회귀 위험이 있으므로 별도 혼합 GPU 검증을 통과하기 전까지 지원 완료로 표시하지 않는다. 이는 아카이브를 분리한다는 뜻이 아니라, 전체 DRM 세트를 적용할 때 호스트의 Intel 그래픽 동작도 확인한다는 검증 조건이다.

## SPK 내부 구성안

```text
syno-amdgpu-runtime-<version>-7.4-<platform>-k<kernel>.spk
├── 기존 사용자 공간 런타임
│   ├── Mesa radeonsi VA-API / RADV Vulkan
│   ├── libdrm / libva / Vulkan loader
│   ├── vainfo / vulkaninfo 및 FFmpeg 래퍼
│   └── Jellyfin 설정 보조 기능 (지원 정책을 통과한 타깃만)
├── driver-assets/<platform>-7.4-kernel5.10.55/  # 각 플랫폼별 전체 DRM 묶음
│   ├── drm-modules.tgz                          # 원형 보존
│   └── SHA256SUMS + target.conf
├── driver-assets/firmware/                      # 두 펌웨어는 한 번만 동봉
│   ├── firmware-amdgpu.tgz
│   ├── firmware-i915.tgz
│   └── SHA256SUMS
├── manifest/inputs.sha256                   # 모든 입력 체크섬
└── 설치·업그레이드·복구 스크립트
```

압축 아카이브 자체를 SPK에 넣고 설치 시 안전한 임시 위치에서 검증·해제한다. 아카이브 경로에 `..`가 있거나, manifest와 체크섬이 일치하지 않거나, 예상 타깃과 다른 모듈 메타데이터가 발견되면 설치를 중단한다.

## 설치 및 부팅 적용 흐름

1. **사전 검사:** DSM 버전, 플랫폼, `uname -r`, CPU 아키텍처, PCI AMD GPU, 현재 DRM 모듈 상태를 읽는다. 선택된 패키지의 커널 ABI와 지원 플랫폼 목록에 일치해야 한다.
2. **호환성 확인:** SPK 안의 타깃 식별자, 모듈 `vermagic`, 파일 체크섬을 확인한다. `x86_64`만 같다는 이유로 설치를 허용하지 않는다.
3. **백업 및 스테이징:** 기존에 같은 목적지에 있던 모듈·펌웨어를 파일 단위로 백업하고, 패키지가 추가하거나 교체한 파일을 manifest에 기록한다. 백업 저장공간 확보에 실패하면 변경하지 않는다.
4. **DRM 세트 배치:** 전체 타깃 묶음을 DSM 모듈 검색 경로에 스테이징하고 필요한 모듈 인덱스를 갱신한다. DSM/로더별 모듈 로딩 순서가 확인된 방식으로만 부팅 적용을 연결한다.
5. **펌웨어 배치:** `firmwareamdgpu.tgz`의 AMD 펌웨어와 `firmwarei915.tgz`의 Intel 펌웨어를 각각 `/lib/firmware/amdgpu/`, `/lib/firmware/i915/`에 배치한다. 기존 파일은 덮기 전에 백업하고, 제거 시 패키지가 소유한 파일만 복구·삭제한다.
6. **재부팅 안내:** 이미 DRM 모듈이 로드되어 있으면 이를 강제로 내리지 않는다. 설치 상태를 “다음 부팅 적용 대기”로 표시하고 재부팅 후 실제 로드된 모듈의 경로·버전을 다시 확인한다.
7. **런타임 활성화:** AMD render node가 확인된 뒤에만 사용자 공간 런타임 검증과 지원 타깃의 Jellyfin 연동을 수행한다. 노드가 없으면 자동 설정을 건너뛰고 원인을 기록한다.

DSM 빌드와 로더 구성에 따라 모듈이 SPK 설치 스크립트보다 먼저 로드될 수 있다. 따라서 실제 구현 전 부팅 순서와 모듈 검색 경로를 각 지원 환경에서 검증해야 한다. 검증되지 않은 경로에서는 설치를 거부하거나 명확히 수동 재부팅/복구 안내를 제공한다. 로드된 DRM 모듈의 `rmmod`/강제 교체는 금지한다.

## 업그레이드 및 제거

- 업그레이드는 먼저 새 SPK의 플랫폼·커널·체크섬을 모두 검사한 뒤 staging 영역을 준비한다. 준비가 완료된 경우에만 파일 교체를 진행한다.
- 교체 파일별로 원본 백업, 새 파일 체크섬, 패키지 소유 여부를 manifest에 기록한다. 다른 패키지나 DSM이 이후 교체한 파일은 무조건 덮어쓰거나 삭제하지 않는다.
- 롤백은 백업 manifest를 기준으로 파일 단위 복원 후 `depmod` 등 인덱스를 갱신하고 재부팅을 요구한다. 실행 중인 모듈은 언로드하지 않는다.
- 제거 시 패키지가 추가한 파일과 패키지 설치 직전 상태를 확인해 정확히 복원한다. AMD 펌웨어가 다른 패키지에서도 사용 중일 수 있으므로 출처 불명 파일이나 기존 파일은 삭제하지 않는다.
- Jellyfin/Plex 설정 복구는 기존 헬퍼의 백업·검증 절차를 유지한다. 커널 4 타깃의 기존 비활성화 정책은 별도 안정화 검증이 있기 전까지 유지한다.

## 보안과 실패 처리

- 설치 스크립트는 루트 권한을 사용하므로 외부 다운로드를 설치 시점에 수행하지 않는다. 모든 바이너리 입력은 빌드 시 고정하고 SPK 안에 동봉한다.
- tar 해제 전 경로 순회, 절대 경로, 링크 탈출을 검사한다. 예상된 목적지 외부로 파일을 쓰지 않는다.
- 지원하지 않는 DSM/플랫폼/커널 조합, 체크섬 불일치, 백업 실패, 로드 상태 불명, 기존 모듈 충돌 시 fail-closed로 종료한다.
- 설치 로그에는 판별된 타깃, 모듈 `vermagic`/`srcversion`, 적용 파일과 백업 경로, 재부팅 필요 여부를 남긴다. 비밀정보나 사용자 미디어 경로는 기록하지 않는다.

## 단계별 구현·검증 계획

### 0단계 — 빌드 입력 고정

- 26.9.12의 16개 DSM 7.4 DRM 자산을 체크섬과 함께 `build/sources.lock`에 등록한다.
- AMD 및 i915 펌웨어 아카이브를 각각 출처·버전·SHA-256으로 고정한다.
- 모든 모듈 아카이브의 내부 경로, 파일 목록, `vermagic`, 의존 관계를 자동 검사한다. AMD/i915 파일 선별이나 제거는 하지 않는다.

### 1단계 — DSM 7.4 kernel 5 통합 SPK

- `epyc7002`에서 DRM 전체 묶음과 AMD/i915 펌웨어 통합을 실기 검증한다. 통과 후 여섯 K5 플랫폼의 DRM 묶음을 단일 SPK에 추가하고 설치 시 자동 선택하도록 한다.
- 깨끗한 부팅 적용을 대상으로 설치→재부팅→모듈/펌웨어 로그→`/dev/dri/renderD*`→`vainfo`→FFmpeg→Jellyfin VA-API 순서로 검증한다.
- 기존 로더 모듈과 SPK 모듈이 혼재하지 않는지 확인한다. 실패 시 자동 복구와 롤백을 검증하기 전에는 다음 플랫폼으로 확대하지 않는다.

### 2단계 — DSM 7.4 kernel 4 통합 SPK

- `geminilake`에서 kernel 4.4.302 전체 DRM 묶음과 동일한 AMD 펌웨어를 대상으로 독립 검증한다.
- 커널 로그, 모듈 로드, render node, 장시간 DRM 안정성을 우선 확인한다. kernel 4의 Jellyfin/Plex 자동 연동은 기존 안전 정책대로 비활성화한다.

### 3단계 — 지원 매트릭스 확대

- 단일 K5 패키지의 전체 입력 체크섬·플랫폼 메타데이터·압축 콘텐츠를 검증한다.
- 실제 플랫폼 또는 동등한 부팅 검증을 하지 않은 대상은 “패키지에 포함됨”과 “실기 검증됨”을 구분해 공개한다.
- kernel 4.4.302와 DSM 7.3→7.2→7.1→7.0은 별도의 커널 호환성 설계와 검증 후 추가한다.

### 성공 판정

- SPK 메타데이터의 플랫폼과 커널 대상이 실제 장치와 일치한다.
- 부팅 후 로드된 `amdgpu` 및 의존 DRM 모듈이 의도한 타깃 묶음에서 왔고, 펌웨어 로드 오류가 없다.
- render node와 VA-API가 정상 동작하며, 지원 대상으로 표시한 미디어 서버 경로에서 트랜스코딩이 확인된다.
- 업그레이드·제거·복구 테스트가 DSM의 기존 파일을 손상시키지 않는다.

## 현재 상태와 범위

DSM 7.4 kernel 5.10.55 `epyc7002` 파일럿에서는 모듈, 펌웨어, VA-API 런타임 동작을 검증했다. 릴리즈에는 K5 6개 및 K4 10개 플랫폼의 DRM 묶음을 각각 동봉한 두 SPK가 포함된다. 두 빌드는 입력 체크섬과 필수 `amdgpu.ko`/`i915.ko` 파일을 확인한다. AMD/i915를 분리하거나 DRM 아카이브에서 한쪽을 제거하지 않는다. 패키지에 포함된 것과 실기에서 검증된 것은 구분해 안내한다. K4 미디어 서버 자동 연동은 비활성화되어 있으며 VA-API는 실험적이다.
